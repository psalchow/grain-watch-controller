# Tenants — Implementation Plan

**Spec:** `docs/superpowers/specs/2026-09-20-tenants-design.md` — decisions and
rationale live there; this file is the route through the code.

**Goal:** Replace the per-user hall list with tenant membership. A hall belongs
to one tenant, a user to one or more, an administrator sees everything.

## Decisions that constrain the work

| | |
|---|---|
| Token claim | `tenants: [{ id, name }]` — ids authorise, names are display data |
| Request body | `tenantIds: string[]`, capped at **one** entry by Zod |
| Foreign hall | keeps answering **403**, unchanged |
| Tenants | created with SQL; the API only lists them |
| Out | deactivation flag, tenant CRUD, unique names |

The claim and the body field are different things. The cap is the only mechanism
keeping multi-tenant users out of existence, so it belongs on **both**
`createUserSchema` and `updatePermissionsSchema`.

## Task 1 — Backend

One task, one commit: `ts-jest` type-checks every transformed file and
`repositories/`, `services/auth/` and `models/` are named re-export barrels, so
removing `stockAccess` compiles all at once or not at all. Intermediate states
are red by construction; do not chase them.

**Data layer**
- `schema.ts`: add `tenants` (id, name, created_at) and `user_tenants`
  (composite PK, index on tenant_id); add `stocks.tenantId`; delete
  `userStockAccess`.
- Migration 0005, hand-edited after `drizzle-kit generate`: create tables,
  insert `tnt_default` ("Standard"), backfill one membership row per user,
  `ALTER TABLE stocks ADD tenant_id … DEFAULT 'tnt_default' NOT NULL`, then drop
  `user_stock_access` **last**.
- `TenantRepository`: `findAll`, `findById`. Nothing else — tenants are not
  created through code.
- `UserRepository`: membership replaces grants, joined to `tenants` for the name.
- `DEFAULT_TENANT_ID` lives in `schema.ts`, beside the table whose row the
  migration inserts — `seed.ts` seeds stocks, and importing it from
  `services/auth/` to create the bootstrap admin would cross a layer for a
  constant. Seeded halls carry it.
- `initializeDefaultUsers` is the only user created outside the admin API and
  runs on a fresh database right after the migration. It takes
  `tenantIds: [DEFAULT_TENANT_ID]`.

**Model and services**
- `TenantRef = { id, name }`, `User.tenants`, `UserProfile.tenantIds`.
- `hasStockAccess(user, stock)` — takes the hall now, not its id. The `['*']`
  convention goes.
- `UserService`: `tenantIds` in and out; delete the unused `canAccessStock`.
  `UserProfile` carries ids only — it feeds `req.user` and the predicate, which
  need nothing else. So the admin responses, which the spec requires to carry
  names, are projected from the **full user**, not from the profile:
  `createUser` already re-reads it for `active` and `createdAt`, and
  `updateUserPermissions` gains the same re-read. One query, and the three
  admin routes then really do answer one shape.
- `AuthService`: sign and verify `tenants`; reject a payload without it.

**HTTP**
- `requireStockAccess` becomes `async`: administrator passes, otherwise look the
  hall up and compare tenants. 403 as before.
- `listStocks` filters by the same predicate.
- `login` answers `tenants`; `refresh` is unchanged.
- Admin: `tenantIds` on create and on permissions, validated against existing
  tenants; new `GET /admin/tenants` (list only).
- Delete `updateUserSchema` / `UpdateUserRequest` — unrouted, and now describing
  a retired concept.

**Tests** — the sweep is mechanical; let the compiler find the sites.

```bash
grep -rn "stockAccess" backend/     # must return nothing when done
grep -rn "deviceGroup:" backend/tests   # Stock literals needing tenantId
```

Convert by shape: `User` fixtures and JWT payloads take `tenants`,
`UserProfile` / `req.user` literals take `tenantIds`, request bodies take
`tenantIds`. New coverage worth having beyond the rename:

- membership with two tenants reaches halls of both (the read path is
  multi-valued even though no endpoint writes it);
- `requireStockAccess`: own tenant, foreign tenant, unknown hall, administrator;
- a token carrying the retired claim is rejected;
- `stocks.test.ts`: move `grain-watch-2` to a second tenant in the fixture so the
  existing 403 and list-filter cases keep testing something. Without that both
  halls sit in `tnt_default` and those cases go green while covering nothing.

**Done when:** `npm test --workspace backend && npm run typecheck --workspace backend`.

## Task 2 — Frontend

- `types/api.ts`: `stockAccess` → `tenants` / `tenantIds`.
- `lib/token.ts`: decode the payload as UTF-8 (below). Its test fixture has to be
  built with `TextEncoder` — `btoa` throws on an umlaut, so an ASCII-only helper
  cannot express the case.
- `api/auth.ts`: `userFromToken` reads `tenants`. This is load-bearing — left on
  the old claim it returns `null` for a valid token, and every session silently
  fails to restore.
- `api/admin.ts`: `listTenants()`.
- `AdminUsersPage`: hall multi-select → single tenant select, sending a
  one-element `tenantIds`. Both roles need one.
- `Header`: tenant name beside the username, only for a non-administrator with
  exactly one tenant. Once, in the wide bar — the phone layout's username is a
  `Dialog` title typed as `string`.

Same sweep as the backend, same gate:

```bash
grep -rn "stockAccess" frontend/    # must return nothing when done
```

It catches the two test files the list above does not name,
`lib/access.test.ts` and `components/Header.test.tsx`.

**Done when:** `npm test --workspace frontend && npm run typecheck --workspace frontend`.

## Traps

Each of these cost a review round. They are the reason this plan exists.

**SQLite refuses `ADD COLUMN` with both `REFERENCES` and a non-null default**
while `PRAGMA foreign_keys = ON`. Hence `stocks.tenant_id` has no foreign key.
Do not rebuild `stocks` to add one — `fan_state` and `fan_events` reference it.

**The migration widens access.** Every user lands in `tnt_default`, so anyone
holding a partial hall grant gains the rest, and `DROP TABLE user_stock_access`
destroys the evidence. The operator must run this *before* upgrading:

```sql
SELECT u.id, u.username, COUNT(a.stock_id) AS granted
FROM users u
LEFT JOIN user_stock_access a
  ON a.user_id = u.id
 AND (a.stock_id = '*' OR a.stock_id IN (SELECT id FROM stocks))
GROUP BY u.id, u.username
HAVING SUM(CASE WHEN a.stock_id = '*' THEN 1 ELSE 0 END) = 0
   AND COUNT(a.stock_id) < (SELECT COUNT(*) FROM stocks);
```

It starts from `users` so an account with no grant at all is listed, treats `'*'`
as full access, and ignores grants naming halls that no longer exist.

**Nobody is forced to log in again.** The old access token is rejected, but the
refresh cookie survives and the client re-mints silently — on mount and on the
first 401. Say that in `DEPLOYMENT.md` rather than promising a forced re-login.

**`decodeJwtPayload` uses `atob`**, which reinterprets bytes as latin1: `Müller`
becomes `MÃ¼ller`. Latent while only the username came through it; tenant names
make it visible. Decode with `TextDecoder` — and note that `btoa` cannot build a
test fixture containing an umlaut, so encode those with `TextEncoder`.

**`jest.mock` is hoisted above the requires.** A factory closing over a `const`
declared beside it throws `ReferenceError` before the suite runs. Declare the
mock inside the factory and pull it back out with `jest.requireMock` — the
pattern is already in `tests/integration/stocks.test.ts`.

**`models/index.ts` is an explicit re-export list**, not `export *`. A new type is
invisible to importers until it is listed there.

**Drizzle throws on `.values([])`.** Keep the emptiness guard around the
membership insert that the grants insert already has.
